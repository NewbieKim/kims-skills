# 章节深化与总结流程

本流程是完整章节学习的顺序要求；章节可以跨多次会话。每次开始先确认章节、当前阶段和上一阶段产物。临时单题问答不自动升级为完整章节。

## 1. 系统讲解本章

先定义章节边界与先修知识，再完整梳理本章核心概念、组成、运行机制、典型数据流、失败模式和工程取舍。按用户已有全栈背景解释，不假定只会概念的 RAG/Memory 已做过实践。给出必要例子与自检要点，让用户有机会提问；未完成讲解前不以模拟面试替代教学。

## 2. 代码对照与差距清单

按 [工作区代码地图](workspace-code-maps.md) 定位后，重新读取真实入口和调用链。逐个知识点注明：项目及文件/函数、当前实际路径、**已实现/部分实现/未实现**、证据、与面试及生产工程要求的差距。未实现时直接写“未实现”，不能把注释、常量、计划或另一条聊天链路当成此路径已运行。将待实现功能整理为有优先级的要点，并给用户一份有限的读码范围和阅读问题。等待用户确认已读或完成读码交流，再进入阶段 3。

## 3. 读码后的第一轮面试

读取 [面试训练体系](interview-training.md)。模拟真实面试官，一次一题，先让用户作答，再追问机制、代码证据、失败路径和取舍。分别记录主答、追问、评分、正确点和缺口；不事先泄露答案。此轮重点检验理解现状，不能把设计中的功能冒充已实现。未达标可解释并复测，但不替用户答题。

## 4. 用户实作与审改

从差距清单中选择章节内的真实业务功能。先给**大概实现框架**：业务目标、允许改动范围、接口/状态与数据流、关键边界、失败场景、测试和验收命令；不直接给完整可复制实现。用户自己写关键代码；用户明确要求代写时才代写。完成后读实际 diff，运行相关类型检查和确定性测试，按正确性、可维护性、安全、观测与面试可讲述性指出问题，给出下一轮最小修改建议。迭代至验收通过；外部依赖不可用时区分已验证与待集成验证。

## 5. 实作后的第二轮面试与章节通关

以用户真实改动和测试为素材，再做一次模拟面试，重点追问为什么这样设计、失败如何恢复、怎样证明有效、尚未解决什么。章节通关需兼具完整知识解释、真实代码定位、用户实现与验证、两轮面试和 wiki 沉淀；未满足则明确标记阶段与缺口，不按日期自动通关。

## 按需生成 daydayup 总结

仅在章节完成、且用户明确提出总结请求时，写入 `D:\kimsweb\kims-skills\agent-development-engineer-guide\daydayup\MMDD知识点名称.md`。`MMDD` 取用户提出总结当日的月日，知识点名称简短且适合文件名；同名总结应更新而不覆盖无关内容。先核实当时的代码与验证结果，再写：

1. **概念**：定义、机制、边界、常见误区、工程取舍。
2. **对应关键代码实现**：项目/文件/函数、调用链、状态真相源、关键逻辑、测试命令和实测结果；区分已实现、部分实现、未实现。
3. **面试题汇总**：按基础机制、项目读码、生产故障、设计取舍等类别整理每题；提供真实面试回答框架（结论→机制→项目证据→权衡→验证）、重要细节、常见失分点与加分项。不得编造线上指标或把待实现描述为业绩。

总结文件是用户的章节复习材料；仍按 [知识库沉淀工作流](knowledge-base-workflow.md) 更新 `kims-llm-wiki` 的相关记录和日志，不用总结文件取代 wiki。
