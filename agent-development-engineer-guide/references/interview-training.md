# 面试训练体系

完整章节学习时，仅在用户完成该章代码阅读后进行第一轮面试，在用户完成待实现功能并通过验证后进行第二轮；独立模拟面试可直接使用本体系。题目要检验本阶段已有证据，不把尚未讲解或未实现的项目功能当作已掌握。

## 题目来源与取舍

使用 AgentGuide 三套题库作为覆盖清单，不逐字背诵答案：

- 理论篇覆盖 Transformer/Attention、位置编码、MHA/MQA/GQA、模型架构、解码、Tokenization、KV Cache、推理优化等。开发岗优先掌握机制与工程影响；VLM、RLHF、分布式训练保留到目标 JD 需要时。
- RAG 篇 22 题全部进入核心池：流水线、切块、Embedding、混合检索、Lost in the Middle、评估、增量更新、噪声、BM25、意图识别、延迟和搜索工具污染。
- Agent 篇 52 题全部进入核心池：Agent/ReAct/规划、Memory、Tool Use、框架、多 Agent、A2A、并发调度、容错、JSON 稳定性、隐私越权、评测和 bad case 闭环。

## 单题流程

1. 只给问题和场景，不给提示。
2. 用户先在限定时间内作答：基础题 90 秒，系统题 5-10 分钟起步。
3. 追问至少两层：机制/边界；项目/数据；替代方案/故障。
4. 给 0-4 分和一条最重要的改进建议。
5. 用户重新回答一次，合格答案进入 wiki；错误模式进入错题页。

## 通用回答骨架

**定义 → 机制 → 项目证据 → 权衡 → 验证指标。**

示例不是背诵模板：先一句话定义 RAG，再拆索引/检索/生成，指向 kims-llm-wiki 实践，解释 chunk/召回/延迟权衡，最后给 Recall@K、MRR、Faithfulness 和 P95 延迟。

## 评分标准

| 维度 | 0 | 2 | 4 |
|---|---|---|---|
| 准确性 | 核心错误 | 主体正确、有遗漏 | 准确且能指出条件 |
| 机制深度 | 只背名词 | 能讲主要流程 | 能讲状态、复杂度和失败路径 |
| 项目证据 | 无例子 | 有泛化例子 | 可定位代码、测试和指标 |
| 工程权衡 | 只说优点 | 能比较两方案 | 能结合约束作决策和降级 |
| 表达 | 散乱超时 | 结构基本清楚 | 先结论、层次稳定、追问不崩 |

总分 20；16 分进入间隔复习，12-15 分一周内复测，低于 12 分进入下一次训练。

## 动手题池

所有题先限定真实项目，再给验收：

1. 在 `ltbot-server` 实现有最大步数、超时、取消和未知工具处理的 Tool Loop。
2. 为 ltbot 两套工具注册设计单一契约，使用 zod 验证参数并生成模型 schema。
3. 为危险 MCP 工具增加确认令牌、审计记录与幂等键。
4. 为 `remote-chat-sdk` 构造跨 chunk SSE、断行 JSON、取消和错误事件测试。
5. 为 `workflow/router.ts` 建路由混淆集，测准确率、低置信降级和 schema 失败。
6. 为 kims-llm-wiki 实现 Markdown 切块、增量指纹和父子引用。
7. 实现 BM25/关键词与向量结果的 RRF 融合，做 Top-K 消融。
8. 为 RAG 建分层 30 题集，分开测检索、引用与回答忠实度。
9. 将 LangGraph MemorySaver 的限制设计成可持久化 checkpointer 接口并验证恢复。
10. 给工具调用增加超时、指数退避、熔断、幂等和明确错误分类。
11. 设计统一 Trace：request/session/step/model/tool/retrieval/token/cost/error。
12. 对 prompt injection、越权工具、敏感信息回显、资源耗尽做红队测试。

## 系统设计题池

### 企业知识助手

必须覆盖多格式摄入、增量索引、Hybrid+Rerank、引用、权限过滤、多租户隔离、评测、观测、无答案和成本。

### 日常工作 Agent

基于 `kims-dailywork-mcp` 设计工单/邮件编排：读写权限、草稿/发送 HITL、幂等、重试、审计、会话配置隔离和故障恢复。

### 浏览器 Remote Agent

基于 `web-mcp-sdk + ltbot + ltbot-server` 设计工具发现、页面状态同步、危险动作确认、session TTL、断连恢复、并发和 replay。

### 多租户 Agent 平台

基于 `ain-agent-sdk` 设计 workflow registry、模型路由、状态存储、队列、限流、trace/eval、版本发布与回滚。

## 项目深挖追问

- 为什么这里是 Workflow 而不是 Agent？
- 状态真相源在哪里？前端、Redis 和 LangGraph 如何避免冲突？
- 模型输出非法 JSON、工具超时、重复执行时会怎样？
- 为什么选择自研 SDK，而不是直接用成熟框架？
- 怎样证明路由/RAG/Prompt 优化真的有效？
- 最大并发、P95、成本、错误率目前是多少？没测过如何补测？
- 哪个设计最失败？如何发现并修正？
- 如果换模型、换向量库或换业务，哪些层无需变化？

## 模拟面试组合

- **30 分钟快测**：3 理论 + 2 RAG/Agent + 1 项目追问。
- **60 分钟技术面**：理论 10 分钟、读码 15 分钟、编码 20 分钟、项目 15 分钟。
- **90 分钟全真面**：加 30 分钟系统设计与最后反问。

每次只记录真实表现。不要提前把答案写进题面，也不要用用户刚看过的原句作为唯一通过标准。
