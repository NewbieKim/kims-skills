# 需求分析与拆解

## 何时使用

- 用户提供需求说明、原型、截图、Story、接口文档或业务规则。
- 需要判断需求能否开发、改哪些页面、涉及哪些接口和权限。
- 需求不完整，需要输出问题清单、边界场景和验收标准。
- 需要把大需求拆成可开发、可联调、可测试的任务。

## 分析框架

优先按 `Given / When / Then` 描述业务场景：

- Given：前置条件，如角色、登录态、业务状态、权限、数据来源。
- When：用户动作或系统事件，如点击、查询、提交、导出、上传、路由进入。
- Then：系统结果，如页面展示、接口调用、状态变化、提示文案、后续流转。

同时补充：

- 正常路径、异常路径、空数据、重复操作、弱网、接口失败。
- 权限点、按钮可见性、按钮可点击条件。
- 路由入口、返回链路、详情页跳转、菜单入口。
- 字段来源、字段格式、必填规则、金额精度、日期范围。

## 项目约束

- 页面落位遵循角色目录：通用 `src/views/common/`，供应商 `src/views/SPY/`，核心企业 `src/views/CE/`，资金方 `src/views/CPT/`，运营 `src/views/OPE/`，集团 `src/views/GROUP/`。
- 新增页面或入口变更必须同步检查 `src/routes.js`。
- 接口定义统一放在 `src/api/`，页面层只消费接口结果。
- 金额计算必须使用 `decimal.js`，展示默认保留 2 位。
- 列表查询默认分页，禁止全量拉取后前端分页。
- 用户可感知失败必须有 `$llsAlert`、`$llsMessage` 或 `$llsConfirm`。
- 涉及上传、预览、协议、评价、问卷、单据模块时，优先复用项目已有全局能力。

## 工作流程

1. 读取需求、原型、接口文档和相关历史页面。
2. 识别用户角色、业务状态、页面入口和操作链路。
3. 拆解页面、组件、接口、字段、权限、校验、提示和路由。
4. 按 `Given / When / Then` 补齐正常、异常、边界场景。
5. 标记风险点、依赖项和待确认问题。
6. 输出开发任务清单和验收标准。

## 输出模板

```markdown
## 需求概述

[一句话说明业务目标和影响范围]

## 场景拆解

- Given [前置条件]，When [用户动作]，Then [系统结果]。
- Given [异常/边界条件]，When [用户动作]，Then [失败提示或兜底结果]。

## 页面与组件

- 页面：[路径或待新增路径]
- 组件：[复用/新增组件]
- 路由：[是否新增或修改 src/routes.js]

## 接口与字段

- 查询接口：[接口名/路径/入参/出参]
- 提交接口：[接口名/路径/入参/出参]
- 字段规则：[必填、格式、金额、日期、枚举]

## 权限与状态

- 角色：[可见范围]
- 按钮：[可见/可点条件]
- 状态流转：[业务状态变化]

## 风险与待确认

- [风险或待确认问题]

## 开发任务

- [ ] 页面结构
- [ ] 接口封装
- [ ] 交互与校验
- [ ] 权限与路由
- [ ] 自测与联调
```

## 自检清单

- [ ] 是否覆盖正常、异常、空数据和重复操作。
- [ ] 是否明确页面路径、路由、接口、字段和权限。
- [ ] 是否识别金额精度、分页、大数据量、导出和上传风险。
- [ ] 是否列出后端、产品、测试需要确认的问题。
- [ ] 是否形成可执行的开发任务和验收标准。
