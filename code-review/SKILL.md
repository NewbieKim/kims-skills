# 前端代码评审（Code Review）

## 何时使用本 Skill

- 评审 Merge Request / Pull Request、本地分支 diff、或指定文件。
- 用户要求「按团队规范检查」「有没有明显问题」「走读这段逻辑」。
- 与 `.cursor/skills` 中 **vue2-table-page**、**vue2-dialog** 等规范对照：列表页/弹窗类改动优先核对对应 Skill。

**可选团队文档**（若可访问，与本文互补）：  
https://doc.linklogis.com/books_space/62736e2d026ee7001506965f/view/65fba74188f0bb0013ba45f2  

**MCP**：会话中若存在 `dev-standards` / `user-dev-tools` 等开发规范类工具，应先查看可用工具与团队规范资源，再与下列清单合并使用。

---

## 评审原则（执行顺序）

1. **先理解变更意图**：业务目标、接口契约、是否破坏兼容。
2. **先拦高风险**：安全、资金/权限、数据丢失、线上不可回滚。
3. **再抠质量**：风格一致性、可维护性、注释与扩展点。
4. **结论分级**：必须修改（Blocker）/ 建议修改（Major）/ 可选优化（Minor）/ 疑问（Question）。

## （1）代码风格与命名

### 与仓库约定对齐

- **Vue**：单文件组件结构、与现有页面一致的 `data` / `computed` / `methods` 顺序；列表/弹窗结构参考 `vue2-table-page`、`vue2-dialog` Skill 与模板 `src/views/template/`。
- **组件库**：`llsInput`、`llsButton`、`llsTitleBox`、`llsTabs`、`llsSelect` 等用法与项目内同类页面一致；注意 `type="search"|"form"`、`limit`（如 `money`）、`v-model.trim` 等既有模式。
- **样式**：类名与布局（如 `sear-box-201`、`table-total`）与周边页面统一；避免在新代码中引入与全局冲突的随意命名。
- **命名**：组件名 PascalCase；方法/变量 camelCase；常量全大写下划线；文件名与路由/目录习惯保持一致。

### 常见命名与风格问题

- 缩写过度或语义不清（`a1`、`handle` 无上下文）。
- 同一概念多种命名（`userId` / `uid` / `user_id` 混用）。
- 仅为绕过校验的「魔法字符串」散落多处，未抽常量或枚举。

---

## （2）错误、漏洞与健壮性

### 逻辑与数据

- **分支完整性**：`if/else`、`switch`、异步回调是否覆盖失败与边界（空列表、分页末页、重复提交）。
- **判空与类型**：接口返回、`undefined`/`null`、数组长度、`NaN`；对象深层访问是否需可选链或守卫（与当前构建/Babel 能力一致）。
- **布尔误用**：例如 `:disabled="obj.field"` 在 `field` 为字符串时可能「非空即禁用」，需确认是否应为显式布尔或「有值且只读」等业务含义。

### 异步、Loading 与用户反馈

- **请求**：是否处理 `pending`、重复点击、竞态（后返回的请求覆盖先返回的展示）。
- **Loading**：列表/提交/导出是否有加载态；失败是否结束 loading。
- **错误提示**：接口失败是否有用户可理解的提示；是否吞掉异常导致静默失败。

### 安全（前端侧）

- **XSS**：`v-html`、动态 HTML、富文本是否与 `vue-dompurify-html` 或同等策略一致；避免将未过滤的用户输入拼进 HTML。
- **敏感信息**：日志、`console`、埋点是否打印 token、身份证、完整卡号等。
- **链接与跳转**：外链是否 `rel="noopener noreferrer"`（若项目有约定）；`window.open` / 路由参数是否校验。
- **依赖**：新增脚本 URL、第三方包来源是否可信（供应链意识）。

### 金额与数值

- 金额展示/运算是否与项目一致（如 `decimal.js`、格式化函数）；避免直接浮点运算导致精度问题。

## （3）清晰、简洁、可扩展

- **单一职责**：方法过长、组件过大时，是否应拆子组件或抽工具函数。
- **重复代码**：与 DRY 平衡——复制粘贴的列表/弹窗逻辑是否应复用 mixin、组件或公共方法。
- **扩展点**：新需求是否只需改一处；配置项（字典、权限码）是否硬编码到组件深处。
- **状态来源**：可推导状态是否冗余存储；Vuex / 局部 state 边界是否清晰。
- **性能意识**：大列表是否需虚拟滚动或分页（项目现状允许的前提下）；`watch` 是否过重；不必要的深度监听。

---

## （4）注释

- **应有注释**：非显而易见的业务规则、接口字段含义、与产品/运营约定的特殊逻辑、临时兼容（含计划移除时间或工单号更佳）。
- **避免无效注释**：复述代码语义的废话注释；过期注释比没注释更有害——评审时标记「注释与实现不一致」。
- **复杂流程**：多分支、状态机式 UI，简短说明「谁先谁后」「禁止操作条件」即可，不必长篇论文。

---

## （5）复杂或高风险需求与功能开关

在以下情况应**建议或要求**功能开关（配置中心、字典、路由级开关、环境变量等，与项目现有能力一致）：

- 新功能影响核心交易、清结算、权限或大面积列表性能。
- 上线后难以快速回滚或数据迁移成本高。
- 依赖外部系统不稳定，需要一键降级或走老逻辑。
- A/B 或灰度发布需求。

评审时检查：开关**默认值**、**关闭路径**是否安全、文档或配置说明是否同步。

## 输出格式建议（便于落地）

对每条问题尽量包含：

| 字段 | 说明 |
|------|------|
| 级别 | Blocker / Major / Minor / Question |
| 位置 | `路径:行号` 或 diff 片段 |
| 问题 | 一句话说明 |
| 建议 | 可执行的改法或替代方案 |

示例：

- **[Major]** `src/views/.../foo.vue:42` — 提交未防重复点击，可能导致重复下单。建议：提交前置 `loading` 或禁用按钮，请求结束再恢复。
- **[Question]** `bar.vue:88` — `:disabled="x.y"` 中 `y` 为字符串，是否为「有值即禁用」？若仅只读展示，建议改为显式条件或注释说明。

---

## 自测清单（提交前可对照）

- [ ] 主要路径手动点过；错误接口/空数据看过界面。
- [ ] 新增或修改的接口字段与后端契约一致。
- [ ] 无调试代码（`debugger`、多余 `console`、mock 误提交）。
- [ ] 与相邻页面风格、组件用法一致。

---

## 与项目其他 Skill 的协作

- **列表页**：对照 `vue2-table-page`（`pageCache`、`llsTabs`、`sear-box-201`、分页与导出等）。
- **弹窗**：对照 `vue2-dialog`（`llsFormDialog`、校验、提交与关闭）。
- 若评审范围仅限样式微调，仍应快速扫一眼事件与数据流，避免「只改 class 却破坏 v-if」类问题。
