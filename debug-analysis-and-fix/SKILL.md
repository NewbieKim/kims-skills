# Debug 分析与修复

## 何时使用

- 页面报错、白屏、按钮无响应、表格数据异常、弹窗状态错乱。
- 接口返回正常但页面展示不对，或页面入参正常但接口入参不对。
- 权限、路由、缓存、keep-alive、分页、导出、上传等行为异常。
- 用户要求“帮我定位问题”“修一下 bug”“为什么这样”。

## 调试原则

- 先复现，再定位；先找最小触发条件，再改代码。
- 先看最近变更、调用链和数据流，不凭经验直接改。
- 修复应保持最小范围，不顺手重构无关逻辑。
- 禁止吞异常，失败分支必须有用户反馈或可追踪日志。
- 涉及金额、分页、权限、路由、导出和上传时，额外检查边界条件。

## 定位框架

### 现象

- 什么页面、什么角色、什么入口、什么操作触发。
- 是否稳定复现，是否和环境、账号、数据状态有关。
- 控制台、Network、接口返回、路由参数和本地缓存是否异常。

### 链路

- 页面入口：路由、参数、权限、菜单。
- 数据来源：接口、sessionStorage、Vuex、props、computed。
- 状态变更：data、watch、生命周期、事件回调。
- 展示渲染：过滤器、枚举、金额、日期、v-if/v-show。

### 根因分类

- 接口契约不一致：字段名、枚举值、数据类型、分页结构变化。
- 状态未重置：弹窗复用、列表多选、Tab 切换、查询条件缓存。
- 异步问题：竞态、loading 未关闭、重复提交、后返回覆盖先返回。
- 权限路由：按钮权限、菜单入口、路由参数、返回链路异常。
- 兼容问题：可选链、浏览器 API、第三方组件差异。

## 修复流程

1. 读取报错文件、相关页面、API 封装和路由。
2. 复现或根据用户描述还原最小场景。
3. 沿事件、接口、状态、渲染链路定位根因。
4. 给出最小修复方案，必要时补充防重复、判空或错误提示。
5. 修改代码后检查 lints，并说明验证范围。
6. 如果无法验证，明确剩余风险和建议验证步骤。

## 修复规范

- 接口失败：复用项目拦截器；必要时增加 `$llsMessage`、`$llsAlert` 或 `$llsConfirm`。
- loading：必须在 `finally` 或等价路径关闭。
- 弹窗：打开前重置数据和错误信息，关闭后不残留上次状态。
- 列表：查询前清空选择项，分页参数和查询条件保持一致。
- 金额：计算使用 `decimal.js`，展示走项目过滤器或统一格式化方法。
- 路由：新增或修改跳转时同步检查 `src/routes.js` 和返回链路。

## 输出模板

```markdown
## 问题结论

[一句话说明根因]

## 影响范围

- 页面：[路径]
- 场景：[触发条件]
- 风险：[是否影响线上主流程]

## 修复方案

- [修改点]
- [为什么这样改]

## 验证结果

- [已验证路径]
- [未验证项及原因]
```

## 自检清单

- [ ] 是否明确复现条件和根因，而不是只描述现象。
- [ ] 是否覆盖成功、失败、空数据、重复点击和刷新返回。
- [ ] 是否没有新增空 `catch`、多余 `console` 或 `debugger`。
- [ ] 是否避免改动无关逻辑。
- [ ] 是否检查相关 linter 或运行可用测试。
