# 优化分析与方案设计

## 何时使用

- 页面慢、首屏慢、列表卡顿、重复请求、导出慢、包体积过大。
- 组件过大、方法过长、重复逻辑多、后续需求难扩展。
- 交互体验差，如 loading 混乱、空状态不清、失败无反馈。
- 用户要求“优化一下”“给优化方案”“重构这块”。

## 优化原则

- 先明确目标和指标，再提出方案。
- 先处理高收益、低风险问题，不做无目标重构。
- 优化不能破坏业务语义、权限、路由和接口契约。
- 大数据量优先后端分页、后端聚合或分批处理。
- 金额、导出、交易类链路优先稳定性和准确性。

## 分析维度

### 性能

- 首屏：路由懒加载、依赖体积、接口并发、无效初始化。
- 请求：重复请求、循环请求、查询条件变化导致的抖动。
- 列表：分页、虚拟滚动、表格渲染、选择状态计算。
- 导出：全量查询风险、前端内存、后端分批导出能力。

### 体验

- loading 是否区分表格、全局、提交和导出。
- 空状态、错误状态、权限不可用状态是否清晰。
- 查询、重置、分页、Tab 切换是否符合用户预期。
- 重复提交、快速切换、弱网场景是否稳定。

### 稳定性

- 异步竞态、请求取消、后返回覆盖先返回。
- 弹窗状态残留、keep-alive 缓存污染。
- 接口字段缺失、枚举异常、深层对象访问报错。
- 上传、下载、预览、协议签署是否复用项目既有能力。

### 可维护性

- 组件职责是否过大，是否需要拆分。
- 公共逻辑是否沉淀到 `src/common/` 或复用组件。
- API 是否统一放在 `src/api/`。
- 命名、目录、样式是否和相邻页面一致。

## 工作流程

1. 明确优化目标：性能、体验、稳定性或可维护性。
2. 收集证据：代码、Network、构建结果、用户路径、接口耗时。
3. 识别瓶颈和影响范围。
4. 给出短期方案和长期方案，说明收益、成本、风险。
5. 若用户同意实施，按最小可回归范围修改。
6. 输出验证方式和残余风险。

## 方案分级

- Quick Win：低风险、低成本、可直接实施，如去掉重复请求、补 loading、拆公共条件方法。
- Structural：中等风险，需要调整组件或数据流，如抽组件、统一 API、优化缓存。
- Architecture：高风险，需要跨模块设计，如导出链路改造、权限模型调整、构建拆包。

## 自检清单

- [ ] 是否有事实依据，而不是泛泛而谈。
- [ ] 是否避免循环请求、全量查询和大数据量前端处理。
- [ ] 是否保留错误反馈和 loading 收敛路径。
- [ ] 是否评估路由、权限、接口和历史页面影响。
- [ ] 是否给出可落地的验证方式。
